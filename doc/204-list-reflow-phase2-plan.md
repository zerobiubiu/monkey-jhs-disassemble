## 2. 四条不变式（设计地基）

| # | 不变式 | 保证手段 |
|---|---|---|
| 1 | **永不丢片**：任何影片任意时刻至少在 1 个清单中 | 「先加后删」执行顺序（§4） |
| 2 | **幂等可重入**：加已存在的片 / 删不存在的片均为安全 no-op | JavDB 接口语义 → 支持续传/重试 |
| 3 | **不超上限**：只向「低于目标(≤501)」的清单加片，加到目标即停 | 规划器 target≤501（doc/202 已保证） |
| 4 | **可中止可恢复**：任意时刻能安全停下并恢复 | 恢复日志 + 幂等（§6） |

> 不变式 1 最高优先：**宁可暂时重复，绝不丢失**。重复是可清理的临时态，丢失不可接受。

## 3. 执行模型

- **串行**（并发锁定 1）：限流最安全、校验最稳、续传最干净；由不变式 3，串行无正确性损失。
- **请求间隔**默认 400ms（自适应临时调大，§7）。
- **批 = 检查点单位**，默认每 20 个操作：存进度 + 刷新 UI + 可选短停顿。批非 API 概念
  （API 一次一个操作），纯为续传/进度/限流节奏服务。
- **试运行闸**：默认先执行前 **K=10** 个操作后**自动暂停**，展示真实结果，用户确认「继续」
  才跑剩余——把任何逻辑 bug 的爆炸半径限制在 10 个操作内。
- 每步复用 VLT `postJavdbListMutation`（写）+ `fetchAuthoritativeCheckboxState`（权威校验）。

## 4. 核心安全设计：先加后删

一个「搬家」(A→B) 拆两步，**顺序强制为先加 B、后删 A**：

1. **需加入目标时**：POST 加入 B。
   - `confirmed`（JavDB 回 success:true）→ 进入删除。
   - `rejected`（success:false）→ **不删 A**，影片留原处，该步记 `failed` 跳过。
   - `unknown`（网络歧义）→ **强制权威校验**：已加入 B → 进入删除；未加入 → 按失败回退。
2. **纯去重时**（影片在 A、C，留 A）：删 C 前**先校验 A 确有此片**；含 → 删 C；不含 →
   跳过（防「删了 C 才发现 A 没有」丢片），记 `skipped_drift`。
3. **删除阶段**：POST 移除来源清单。
   - 成功 → 记完成 + 写回滚日志。
   - 失败（加已成功）→ 影片暂存 A+B（临时重复，可清理），记 `pending_cleanup` 待重试，**不丢**。

**安全性**：影片任意时刻要么在 A、要么在 A+B，**绝不会两边都没有**；加失败则原样留 A，零损失。

## 5. 回退策略（Fallback）

| 层级 | 触发 | 回退动作 |
|---|---|---|
| 单步·加失败 | 加入目标 rejected / 校验未加入 | 不删来源，影片留原处，记 `failed`，继续 |
| 单步·加未知 | 加入返回 unknown | 强制权威校验；已加入→继续删，否则按失败回退 |
| 单步·删失败 | 加已成功但删来源失败 | 影片暂存两处，记 `pending_cleanup`，批末/结束后统一重试 |
| 单步·来源漂移 | 纯去重时保留清单已不含此片 | 跳过删除（防丢片），记 `skipped_drift` |
| 批次·失败过多 | 批内失败率 > 阈值（如 30%） | 暂停该批，告警，等用户决定 |
| 全局·硬限流/掉线 | 连续退避仍 429/403 或会话失效 | 停止执行，存进度，告警，可后续续传 |
| 整次·撤销 | 跑完反悔 | 「撤销本次整理」：按回滚日志逆序执行反向搬运（同样先加后删 + 限速） |

**回滚日志**：每完成一步记录 `{videoId, addedTo, removedFrom}`。既供 `pending_cleanup`
重试，也供**整次撤销**（reverse = 加回 removedFrom、删掉 addedTo）。

## 6. 恢复与续传

- **恢复日志**（复用 VLT pending-journal 模式，localStorage）：执行前写 `{move, status:pending}`，
  成功后清除/标记 done。
- **触发场景**：页面卸载（`beforeunload` 存进度）、崩溃、手动中止、限流暂停。
- **续传**：面板初始化扫描日志 → 发现未完成项 → 提示「检测到上次未完成的整理，是否继续？」。
- **幂等兜底**：续传时对每个待办 move 先读权威态，已完成的自动跳过（不变式 2），只干没干的；
  即使日志指针不准也不会重复/出错。

## 7. 降级策略（Graceful Degradation）

降档阶梯（逐级降速/降范围，而非一碰错整体失败）：

```
正常 pace(400ms)
   │ 429/403/503
   ▼
降速档(间隔×2 退避) ──仍限流──▶ 深度降速(再×2 + 短暂停)
   │                              │ 连续失败超阈值
   │                              ▼
   │                          暂停档(等用户: 继续/更慢/中止) ──继续──▶ 正常 pace
   │ 单步失败
   ├──▶ 跳步档(记为待处理 · 继续)
   │ 会话失效
   ├──▶ 停止档(存进度 · 重登后续传)
   │ 校验接口失败
   └──▶ 降级校验(信任 POST success + 批次盘点 · 标注待人工复核)
```

| 维度 | 正常 | 降级后 | 保住 / 牺牲 |
|---|---|---|---|
| 速度 | 400ms | 指数退避 800→1600→… | 保住「能跑」/ 牺牲速度 |
| 完整性 | 全部搬运 | 跳过失败步跑完其余 | 保住「大部分成功」/ 牺牲全量（失败步末尾汇总） |
| 自动化 | 全自动 | 暂停等决策 | 保住「可控」/ 牺牲无人值守 |
| 校验强度 | unknown 权威校验 + 批次盘点 | 校验接口挂→信任 POST 并标「待人工复核」 | 保住「推进」/ 牺牲置信度（明确标注） |
| 目标可达 | 加到目标清单 | 目标因漂移满→该片留原处/跳过 | 保住「不丢不超」/ 牺牲该片归位 |
| 会话 | 持续执行 | 掉线→存进度停止 | 保住「可续传」/ 牺牲一次跑完 |

**限流响应分类**（驱动降速 vs 停止）：
- `429 / 503` → 限流 → 退避降速。
- `403` → 先刷新 CSRF 重试一次；仍 403 → 判风控/封禁 → 暂停等人。
- 连续 `unknown`（超时）→ 疑似限流 → 退避。
- 检测「需登录」→ 会话失效 → 停止档 + 续传。
- 读 `Retry-After` 响应头（若有）作退避时长依据。

> 实现注记：现 `postJavdbListMutation` 只回传 confirmed/rejected/unknown，不暴露 HTTP 状态码。
> 期2 需一**薄封装**复用同端点 + CSRF 逻辑但**回传 HTTP status + Retry-After**，供降速分类。

## 8. 执行前预检（Preflight）

1. **重新枚举**当前组状态，与期1 规划比对 → 发现**漂移**（期间手动增删）→ 提示「状态已变，
   是否重新生成计划？」。
2. 检查 **CSRF token** 存在。
3. 检查**登录态**。
4. **确认弹窗**：规划摘要（搬 N 部 / 去重 M 部 / 涉及清单）+ 勾选「我理解这会修改我的清单」
   + 试运行数量 K。
5. 通过后才进入执行。

## 9. 执行 UI

- 进度条（已完成 / 总操作数）+ 当前操作描述。
- 实时日志（近 N 条：成功/失败/跳过/限流退避）。
- **暂停 / 继续 / 中止** 按钮 + 当前间隔/退避档位指示。
- 结束**汇总报告**：成功 X · 失败/跳过 Y（列明细）· 待清理重复 Z · 是否可「撤销本次整理」。

## 12. API 参考（实现依据，doc/201 已查实）

加入/移除端点（VLT `postJavdbListMutation` 封装）：

```
POST /users/save_video_to_list
Content-Type: application/json
X-CSRF-Token: <meta[name=csrf-token]>     # getCsrfToken() 自动取
body: { video_id, checked, list_id }       # checked:true 加入 / false 移除
credentials: 'same-origin'                 # 页面内原生 fetch，继承登录态 + Cloudflare 通行
返回: { success: boolean, message: string } # success===true→confirmed / false→rejected / 其余→unknown
```

- 一个请求 = 一个「影片 × 清单」状态变更；搬家 = 移除 + 加入 = 2 请求，纯去重 = 1 请求。
- 即 JavDB 原生「存入清单」勾选框所用端点，稳定可靠。
- 期2 薄封装需额外回传 HTTP status + Retry-After（§7 降速分类用）。

## 13. 风险与缓解总表

| 风险 | 缓解 |
|---|---|
| 丢片 | 先加后删 + 去重前校验保留清单（不变式 1） |
| 限流/封号 | 串行 + 保守间隔 + 指数退避 + 连续失败暂停（§7） |
| 逻辑 bug 批量破坏 | 试运行 K 个先跑先验（§3）+ 期1 dry-run |
| 中断半成品 | 恢复日志 + 幂等续传（§6） |
| 跑完反悔 | 回滚日志 + 一键撤销（§5） |
| 状态漂移 | 预检重枚举比对（§8）+ 去重前校验 |
| 校验接口压力 | 仅 unknown 权威校验 + 批次盘点（非每步全量校验） |
